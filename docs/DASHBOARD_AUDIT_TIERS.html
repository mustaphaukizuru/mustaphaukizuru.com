Member dashboard — audit and remediation

Seven tiers, 31 findings, all built on build/waves and not pushed or deployed. Every number below was measured with a browser, a database or a rule engine — not read off the source. The machine-readable record is embedded at the bottom as #audit-source; regenerate this page from that rather than editing the prose.

Three findings were investigated and rejected before being reported, and one was reported and then retracted. They are listed with the rest, because "we looked and it was fine" is worth as much as a fix to the next person who notices the same thing: dark-mode contrast (the washed-out first render was the cookie-consent scrim, not the theme), ProfileTabs not scrolling (it does — only the affordance was missing), the admin surface being untranslated (it is English by convention: admin.json is 86 bytes and no admin page calls useTranslation), and xl: utilities apparently compiling to nothing (a min-width:1280px grep finds nothing because Tailwind v4 emits 80rem).

Tier 0Things that were broken, not ugly

Endpoints answering 500, dates off by a day, a guard that was never wired.

D0-1 Four member endpoints answered 500 shipped

What
clientProjectController used resolveUserLocale at four call sites with no import, so /member/projects/:id/{events,file-requests,time} and the monthly statement PDF threw a ReferenceError on every request. Introduced by me in T5-5 and extended in T5-18; master was clean.
Why it survived
There was no backend linter, and all 1,890 tests covered the service layer — nothing loaded the controller. The SPA hid it too: useProjectPanels caught every rejection and returned [], so three panels rendered empty instead of failing.
Fixed
One import. Plus eslint.server.config.mjs — correctness rules only, each one justified in the header — wired into npm run lint and into CI. Plus PanelLoadError, so a panel that fails now says which one and offers a retry.
Verify
test/memberProjectEndpoints.test.js, 17 cases: every handler invoked for real, and every module under src/ asserted to load without a ReferenceError.

D0-2 Every due date was a day early shipped

What
new Date("2026-10-01") is midnight UTC. Rendered with a local formatter in any negative-offset timezone — which is every client this business has — it prints the day before. Milestone due dates, invoice dates and statement months were all one day out.
Fixed
formatDay() applies timeZone: "UTC" last, so a caller cannot override it, and null guards were added to the three date formatters. web/vitest.config.js now pins TZ=America/Mexico_City: the bug is invisible in UTC, which is how it shipped.
Verify
web/src/lib/format.test.js, 13 cases — the first asserts the test environment really is negative-offset, or every assertion below it would pass for the wrong reason.

Tier 2The phone

Two of these were invisible in every screenshot, because both defects only exist at phone width.

D2-3 The primary navigation on a phone was not on screen shipped

What
PageTransition set style={{ willChange: "opacity, transform" }} on the wrapper around every route in the app. A persistent will-change: transform makes an element a containing block for position: fixed descendants — so nothing fixed inside a page was fixed to the viewport. It was fixed to the document.
Measured at 375×812
  • The mobile bottom tab bar: top: 1901px — off screen at every scroll position. Five nav destinations, invisible.
  • The mobile nav drawer: 2003px tall, theme control at y=1873 and Sign out at y=1943, both unreachable, because a fixed panel does not scroll with the page.
  • The cookie banner floating mid-page over the cards instead of pinned to the bottom — the thing in the earlier screenshots I had been reading as a z-index problem.
Fixed
Removed. Framer Motion already sets and clears will-change around its own animations; hardcoding it in style keeps it forever and buys a GPU hint for a 240ms cross-fade at the cost of every fixed overlay in the product.
Verify
A systemic guard on the public homepage asserts no containing-block creator contains anything fixed — so this cannot come back through a filter or a contain either.

Tier 3The dashboard could not be read in Spanish

The tier said "twelve hardcoded English page titles". Building it found the reason nobody had noticed them.

D3-3 No URL existed that would render the dashboard in Spanish shipped

What
Language on this site is read off the URL prefix: LanguageWrapper is mounted at the App root and calls changeLanguage(detectLanguageFromPath(pathname)) on every navigation. /dashboard is not /es/…, so it resolved to "en" unconditionally. A member who chose Spanish on the marketing site was switched back to English the moment they signed in, and there was no page they could visit to undo it — the switcher lives only in the public header and footer, and coming back to /dashboard flipped them again.
Scale
es/dashboard.json holds 1,078 translated keys. Only the handful under portal were reachable, through /es/portal/:token, which was mirrored. Everything else had never rendered on a screen.
Why it looked deliberate
A comment in App.jsx: "Admin and Dashboard intentionally NOT mirrored — operator UIs stay English." Admin genuinely is one. The member dashboard is not, and localizeTo.js had encoded the same assumption as /^\/(?:admin|dashboard)/ — which is why every dashboard link was deliberately left unprefixed.
Fixed
  • App.jsx — the fourteen child routes are defined once as a fragment and mounted at both /dashboard and /es/dashboard. React Router's createRoutesFromChildren recurses through React.Fragment, so the two mounts cannot drift.
  • localizeTo.js — NOT_MIRRORED drops to /admin only, so every public page that links into the dashboard (checkout → addresses, success → downloads, signup → dashboard) keeps the reader's language across the boundary.
  • eslint.config.js — the dashboard pages and layout come off the no-restricted-imports exemption list. That exemption is what let ~19 raw <Link to="/dashboard/…"> call sites accumulate across eleven files; all eleven now use the localized variants and the linter holds the line.
  • ProtectedRoute — redirected to the literal "/login", so an expired session on /es/dashboard bounced the member to the English sign-in page. Its spinner label was hardcoded too.
  • pageSeo.shouldNoindex — tested the raw pathname against unprefixed rules. Already wrong before this change: /es/login, /es/signup, /es/checkout and /es/cart are all mirrored and were all being served index,follow while their English twins were noindex.
  • A language control in the dashboard itself — the header from lg, the drawer below it. There was none, and now there is somewhere for it to go.

D6-2 A workaround I wrote and then deleted reverted

What I built
Every chip click routed through the Lenis instance with an explicit -80 offset, on the theory that SmoothScrollProvider owns the scroll position and a native hash jump would fight it. I had a number that seemed to prove it: clicking "Invoices" left the heading 353px down the viewport, repeatably.
What measuring showed
  • Native lands the heading 176px from the top on every target; the Lenis path landed it at 256 — the explicit offset double-counts the CSS scroll margin the browser had already applied. The workaround was worse than doing nothing.
  • The 353px was taken before the empty-state work shortened the page. #invoices then began past the maximum scroll position on a 375px screen, so it could not reach the top of the viewport at all. Clamping, not interference.
Status
Deleted. The anchors are plain anchors, and the reasoning is in the source, because "why is there no scroll handler here" is a question the next person will otherwise answer by adding one.
